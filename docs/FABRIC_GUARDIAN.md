# Nikky Fabric and Guardian

Nikky does not recreate services that already exist. Fabric discovers and orchestrates authorized applications, devices, websites, services, and IoT endpoints through normalized capabilities.

## Fabric execution model

Goal → capability plan → endpoint resolution → permission check → Authority Engine → registered execution method → result verification → audit.

Supported execution-method contracts include APIs/SDKs, OS intents/App Intents/deep links, browser automation, permitted accessibility/UI automation, desktop UI automation, CLI/local services, and IoT adapters. A capability is considered live only when its real platform adapter is configured and verified.

## Transactions

Financial actions such as bills, payments, and purchases are classified as critical risk. Transaction safety adds limits, trusted-recipient/biller controls, duplicate prevention, and confirmation recording. Trusted automation must come from server-side/user-configured policy; action payloads cannot self-authorize.

## Missions

Long-running missions preserve steps and waiting states. Actions requiring review enter Approval Center and correlate the approval back to the exact mission step so the mission can continue without duplicating completed work.

## Guardian

Guardian consumes normalized sensor signals, requires configurable corroboration, checks user responsiveness, and escalates according to preconfigured policy. It can notify the user, contact trusted contacts, and call a configured professional-help integration. Nikky does not assume a direct police/fire API exists, and weak or single-source AI/sensor signals must not trigger professional emergency escalation.

## Health and fitness

Workout planning can adapt to schedule/recovery inputs. Health-signal normalization and anomaly checks are informational safety inputs, not medical diagnosis. Real health-device access requires legitimate platform/device integrations and explicit user consent.
